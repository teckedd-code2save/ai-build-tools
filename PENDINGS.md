# PENDINGS — Known Sharp Edges

A living document of Forge CLI's sharp edges, architecture constraints, and deferred work. Update it whenever you discover a new gotcha; keep entries specific and actionable. Cross-referenced with `AGENTS.md`.

---

## 1. Two `skills/` directories drift [Severity: HIGH]

**What:** `skills/` at the repo root is the source of truth, and `cli/skills/` is a copy packaged into the npm release.

**Why it matters:** Adding or updating a skill in only one location silently breaks the published package — the CLI installs skills from `cli/skills/`, so a root-only change never reaches users. This is the single most common maintenance failure mode in this repo.

**Mitigation:** Run `scripts/sync-skills.sh` after any skill change. CI enforces it via `check-skills-sync.yml` (triggered on pushes touching `skills/**`, `cli/skills/**`, or the sync script).

## 2. `ALL_SKILLS` / `SKILL_DESCRIPTIONS` constants [Severity: HIGH]

**What:** Every skill must be registered in `cli/src/constants.ts` (`ALL_SKILLS` and `SKILL_DESCRIPTIONS`).

**Why it matters:** An unregistered skill is invisible to the CLI — it won't be listed, installed, or validated, even though the directory exists.

**Mitigation:** Update both arrays whenever a new skill is added. Verify with the CLI test suite after registering.

## 3. `installSkill()` copies directories recursively [Severity: MEDIUM]

**What:** `cli/src/setup/skill-writer.ts` installs skills via `fs.cp(source, dest, { recursive: true, force: true })`.

**Why it matters:** No symlinks are involved — the entire directory is copied, and any manual edit inside `cli/skills/` is overwritten by the next sync.

**Mitigation:** Treat `skills/` as the only place to edit skill content. Never hand-edit `cli/skills/`; re-run `scripts/sync-skills.sh` instead.

## 4. `ship-to-vps` installs with placeholder defaults [Severity: MEDIUM]

**What:** The `ship-to-vps` skill ships with `<placeholder>` values in its templates and configuration.

**Why it matters:** A user who scaffolds without a personalization step deploys against placeholder domains, image refs, and credentials — a confusing first-run failure.

**Mitigation:** Treat personalization as a required step after install; document the placeholder variables in the skill's SKILL.md.

## 5. npm publish trigger is path-filtered [Severity: MEDIUM]

**What:** `forge-publish.yml` runs on push to `main` **only when `cli/package.json` or the workflow file itself changes** (plus manual `workflow_dispatch` with a version/tag input).

**Why it matters:** Contrary to the "every push publishes" phrasing in AGENTS.md, a docs-only push does NOT publish. Conversely, any change to `cli/package.json` on main immediately attempts a publish — so version bumps are releases.

**Mitigation:** To publish a new version, bump the version in `cli/package.json` deliberately. Never edit published versions retroactively, and never push `cli/package.json` changes you don't intend to release.

## 6. `check-skills-sync` CI failure means drift [Severity: MEDIUM]

**What:** `check-skills-sync.yml` fails when `skills/` and `cli/skills/` are out of sync (it only runs when skill paths or the script change).

**Why it matters:** A red check on a skill-related PR is drift, not flakiness — merging anyway ships a broken package.

**Mitigation:** Run `scripts/sync-skills.sh`, commit the copied files, and re-push. Never disable or loosen the check.

## 7. MCP config is generated, not maintained [Severity: MEDIUM]

**What:** MCP server configuration is generated by `cli/src/setup/mcp-writer.ts` at setup time.

**Why it matters:** If a skill or its tool files are missing when the config is generated, the emitted config references paths that don't exist, and the MCP server fails at runtime.

**Mitigation:** Regenerate the MCP config after adding or removing skills. Verify referenced tool paths exist before committing generated output.

## 8. CLI commands must follow Commander.js registration [Severity: LOW]

**What:** Commands are registered in `cli/src/index.ts` via `register*Command` functions in `cli/src/commands/`, chaining `.command()`, `.description()`, `.argument()`, `.action()`.

**Why it matters:** Unknown flags are rejected by Commander, and nested subcommands that aren't registered explicitly silently don't exist.

**Mitigation:** Keep command registration centralized in `index.ts`; add subcommands by chaining on the parent command definition.

## 9. ESM-only package [Severity: MEDIUM]

**What:** The package is `"type": "module"` throughout — no `require()`, no `__dirname`.

**Why it matters:** Mixing CommonJS patterns breaks the tsup build and the published package with obscure module errors.

**Mitigation:** Use `import`/`export` and `import.meta.url` exclusively. Run `npm run typecheck` and `npm test` before pushing.

## 10. No direct `console.log` in commands [Severity: LOW]

**What:** Commands must use the `logger` utility from `cli/src/utils/logger.ts`.

**Why it matters:** Direct `console.log` bypasses formatting, pollutes structured output, and breaks tests that capture output.

**Mitigation:** Route all user-facing output through `logger`.

## 11. SKILL.md frontmatter schema [Severity: MEDIUM]

**What:** Every skill's SKILL.md requires YAML frontmatter with `name`, `description`, `version`, `author`, `license`, and `metadata.hermes` tags.

**Why it matters:** Malformed or missing frontmatter breaks skill discovery and validation — the skill silently fails to load.

**Mitigation:** Copy frontmatter from an existing skill when authoring a new one; validate after writing.

## 12. Pinned skills cannot be deleted [Severity: LOW]

**What:** Skills pinned via the hermes curator refuse deletion.

**Why it matters:** A removal attempt fails with a pin-protection error, which can look like a bug.

**Mitigation:** Run `hermes curator unpin <name>` first when a pinned skill genuinely needs removal.

## 13. GitHub Pages serves a hand-maintained landing page [Severity: LOW]

**What:** The Pages site (`https://teckedd-code2save.github.io/ai-build-tools/`) serves `index.html` at the repo root.

**Why it matters:** Landing-page changes deploy on push via the Pages build workflow; breaking `index.html` breaks the public face of the project.

**Mitigation:** Keep `index.html` self-contained and dependency-free; verify locally before pushing.
